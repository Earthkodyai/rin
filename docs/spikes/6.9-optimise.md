## What changed

1. **Vosk without `Gr.fst` (−13 MB in the bundle).** The game always gives Vosk its own grammar (the try's words), which Vosk builds over `HCLr.fst`, so `Gr.fst` (the model's general English grammar, 23 MB) was only read, never used. Vosk still needs the word list inside it: without it the model failed to load ("Could not read symbol table … words.txt"), so the build writes that table out as `graph/words.txt` (2.2 MB, `VoskModelFetch.fstWords`). The unpacked model moved to a new folder name (`small-en-us-0.15-grammar`) and the old 68 MB folder is deleted on first use.
   - **Checked on the phone:** the tester's 40 held-out tries (`tools/stt/recordings/heldout`, git-ignored) replayed through the game's own decoder (`RepeatLabActivity --es replay heldout --ez decoys false`): the same words on all 40 tries with and without `Gr.fst`, and no confidence crossed the 0.6 threshold, so every verdict is the same. The confidences move in the third decimal between any two runs, with or without the change (the control run vs `docs/spikes/3.5/heldout-frozen.jsonl` differs the same way).
2. **Decoration at 30 fps.** The home and editor backdrop (floating breakfast, meteors) and the drifting wallpaper read a clock updated on every frame, so the whole screen, and Rin's WebView with it, redrew 120 times a second. `decorClock()` (ui/common/RinBackdrop.kt) now updates 30 times a second, Rin's own cap on the home screen.
3. **Two leaderboard races** from the code review (`/code-review` over f6abc84..HEAD): a post in flight when posting was switched off could leave the row off the board after switching back on (`TournamentStore.startPosting` now forgets the marks; regression test), and the start page's saves now read and write the entry in one DataStore edit (`updateEntry`).

## Looked at and left

- **Rin's rendering is the home screen's cost.** With the decoration frozen (1 fps) the app still took about 100% of a core and the renderer 50–66%. Rin's fps cap barely moves it (30 / 24 / 20 fps: 175% / 167% / 163% in the debug build). An atrace of 8 s shows RenderThread compositing her WebView (`WebViewFunctor::drawGl`, ~7.7 ms a frame) and the main thread busy in untraced frame callbacks, which is Android WebView producing her frames synchronously from the app's thread. That is the cost of the WebView + three.js design (S2, Plan A), not a bug. Asking the browser for frames only when one is due (instead of three.js's every-vsync loop) made no measurable difference, so it was reverted. Lowering her frame rate or freezing her when idle are product choices, not done.
- **No CPU profile with symbols:** `simpleperf` needs `security.perf_harden` changed on the phone (a security setting), so the trace came from `atrace` (no setting needed).
- **Biggest remaining size items:** Vosk 26 MB in the bundle (the acoustic model and HCLr), native libraries ~10 MB per ABI (Play serves one ABI), Rin's model 6.7 MB, voice 7.9 MB, music 5.2 MB, logos 1.2 MB.
